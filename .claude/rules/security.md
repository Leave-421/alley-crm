# Security

- secret, token, password, private key를 source code에 넣지 않는다. `.env` · `secrets/` · `*.pem`은 커밋하지 않는다(`.gitignore`). `.env.example`에는 이름과 개발용 예시 값만 둔다.
- `.env` 계열 파일 내용을 읽거나 출력하지 않는다(`.claude/settings.json`이 막는다). 설정 확인은 "설정됨 / 미설정"까지만 한다.
- 로그에 인증정보/개인정보(쿠키 · 세션 ID · 비밀번호 · 이름 · 전화번호)를 남기지 않는다.
- 클라이언트 입력은 server에서 다시 검증한다.
- 인증(authentication)과 인가(authorization)를 구분한다.
- UI에서 버튼을 숨기는 것을 권한 검증으로 간주하지 않는다.
- SQL/query/path/url을 사용자 입력과 단순 문자열 결합하지 않는다.
- 새로운 dependency는 필요성과 유지보수 상태를 확인한 뒤 추가한다.
- 보안에 영향을 주는 변경은 PR의 「영향 범위 / 위험」에 명시한다.
- 테스트를 통과시키려고 Spring Security를 전역으로 끄거나 전역 `permitAll()`을 남기지 않는다.

## 인증 · 세션 · CSRF

- Spring Security **서버 세션(HttpSession)** 기반이다. 별도 인증 서버 · JWT를 만들지 않는다.
- 로그인할 때 세션 ID를 새로 발급하고, 로그아웃은 `POST`만 받는다. 비밀번호는 `PasswordEncoder` 해시로만 저장한다.
- 세션 쿠키는 `HttpOnly`, HTTPS에서 `Secure`, `SameSite`를 붙인다.
- **CSRF 방어를 켠다.** 모든 상태 변경 요청에 토큰을 요구한다.
- 인증 안 된 API 요청은 리다이렉트하지 않고 `401 unauthorized` JSON으로 응답한다.

## 역할 · 가게 격리 · IDOR

- 역할은 손님(회원 · 비회원) · 사장님 · 상인회다. 사장님은 직원 계정이 없다.
- 요청마다 로그인 → 골목 접근 → 가게 접근 → 역할 순서로 검사한다.
- 가게 단위 데이터는 **항상 가게 조건으로** 조회한다. 경로의 ID로만 찾지 말고 그 ID가 요청자의 가게 것인지 함께 확인한다 — 다른 가게 것이면 `404 not_found`(IDOR 방어).
- 비회원 손님은 예약번호 + 전화번호로 확인하고, 그 전화번호의 예약만 다룰 수 있는 제한 세션을 받는다. 예약 ID만으로 남의 예약을 열 수 없어야 한다.
- SSE 연결도 같은 세션 쿠키로 인증한다.

## 손님 정보와 공유 (v1 결정 기준)

- 공유 정보(이름 · 연락처 · 인원 · 방문 일시 · 방문한 가게 목록 · 성별 · 연령대)는 **코스 제안과 집계 계산에만** 쓴다. 사장님 화면 · 응답에 다른 가게 방문 이력을 그대로 내보내지 않는다.
- 사장님이 보는 것: 손님이 추천으로 왔는지 여부, 세그먼트는 익명 집단 데이터만. 고객 카드는 우리 가게 방문 이력과 메모만. **보낸 가게 이름 · ID는 예약 · 방문 처리 · 고객 카드 · 수수료 내역 응답에 넣지 않는다.** 손님 흐름은 5명 미만 묶음을 숨긴다.
- 상인회는 가게별 · 골목 전체 집계만 보고, 5명 미만 묶음은 숨긴다. 개인 단위 값은 응답에 넣지 않는다.
- 손님은 흐름 · 매출 데이터를 볼 수 없다.
- 예약 때 공유 동의를 받고, 동의 없이는 예약을 만들지 않는다. 보관 기간이 지난 개인정보는 파기 기능으로 지운다.

## 가상 돈

- 예약금 · 소개 수수료는 가상 잔액이다. 실제 결제 · 송금 API를 부르지 않는다.
- 잔액을 바꾸는 모든 동작은 거래 내역을 남기고, 한 트랜잭션 안에서 처리한다.
