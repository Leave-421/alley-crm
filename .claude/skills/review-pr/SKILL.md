# Review PR

리뷰는 코드 스타일 취향보다 defect risk를 우선한다.

우선순위:
1. 이슈의 요구사항 ID 완료 조건 불충족
2. 계약 불일치 — 경로 · DTO 필드 · enum · 에러 코드가 `docs/CONTRACTS_API.md`와 같은지, 계약에 없는 것을 코드가 먼저 만들었는지
3. 기능 regression
4. 보안/권한 — 세션 · CSRF · 골목 · 가게 접근 검사 · IDOR
5. 개인정보 — 아래 원칙 점검
6. 데이터 손실/잘못된 상태 (예약 상태 전이, 가상 잔액 · 수수료 계산)
7. race condition / 동시 예약
8. error handling
9. 테스트 누락
10. 유지보수성

프로젝트 원칙 점검 (위반이면 blocker):
- **가게 격리** — 사장님 API는 자기 가게 데이터만 돌려준다. 경로의 ID가 다른 가게 것이면 `404`.
- **공유 정보 비노출** — 가게끼리 공유된 손님 정보(다른 가게 방문 이력 등)가 사장님 응답 DTO에 그대로 나가지 않는다. 사장님에게는 "제안으로 왔는지"와 익명 집계만.
- **세그먼트는 익명 집계** — 사장님용 세그먼트 응답에 개인을 식별할 값이 없다.
- **손님 권한** — 손님은 흐름 · 매출 데이터를 볼 수 없다.
- **돈은 가상** — 실제 결제 · 송금 연동이 없다. 잔액 변경은 거래 내역을 남긴다.
- Entity를 응답으로 바로 내보내지 않는다. 스키마 변경은 Flyway 마이그레이션으로만 한다.

각 finding은:
- Severity: blocker / major / minor
- 위치
- 문제
- 왜 문제인지
- 최소 수정 제안

문제가 없으면 억지 finding을 만들지 않는다.
마지막에 "merge 가능 / 수정 후 가능 / 현재 merge 비권장" 중 하나로 결론낸다.
